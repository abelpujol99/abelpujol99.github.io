Farlands: Tiny Harvest

Farlands: Tiny Harvest

Tiny Harvest is a relaxing desktop game that runs while you work, study, or browse the internet. Grow space plants, upgrade your crops, ship, home, and tools, and enjoy a cozy, minimalist experience designed to keep you company throughout your day.
In order to progress, this game counts your keyboard and mouse inputs to keep "playing".

Farlands: Tiny Harvest is a game developed in C with the library Raylib in 3 months.
This was my first project developing in C, and, moreover, I used Raylib, an unknown library to me. I had quite a bit of knowledge of C++, so I had to learn the main differences between these languages, that was not a real problem.
The great struggle came with Raylib. Until that time, it was an unfamiliar library, due to this, it took some time until I understood how the features I needed worked and implemented the necessary code structure and Adapters, which allowed me to display assets without the need to interact directly with the library's code.

This game was developed during my internship at JanduSoft as a spin-off of Farlands. We were only 2 people on the developing team, Eric Rodríguez as a designer and producer, and me as a developer. But, we also received some help from the team of Farlands.
We worked with constant contact and weekly meetings, where we discussed the feasibility of each milestone and which should be the next one.
Plus, we were so well on time that we were able to implement skins.

Pounce Palace

Pounce Palace

Pounce Palace is a first-person platformer game where the player has to acquire movement skills and learn how to use them in order to defeat the enemies in their path to complete the level.
This game was developed in Unity.

The foes are controlled by an AI, and this has to decide which is the most optimal action. Some enemies are static, but some others can move along the level. The Pathfinding computations can't reside in the main thread while trying to keep the game at 60 FPS, so I needed to implement multithreading to handle pathfinding algorithm calculations.

Implementation

To balance game performance and enemies' movement fluidity, the number of threads and the time elapsed to refresh the enemies' path must be easy to tweak.

To modify them easily those fields were exposed in the editor.

In order to balance the work per thread, enemies' pathfinding calculations would be distributed between threads equitably.

To accomplish this requirement the threads work with a list filled with enemies' id, and those are distibuted when the enemies have been spawned and removed when they are defeated.

The thread is not the one that has the necessity to execute the pathfinding algorithm in sequence when the time limit expires; it is each enemy that needs it. Thus, it would reduce resting times.

In order to achieve this milestone, each enemy has a timer assigned. An enemy is selected to calculate their path when the timer exceeds the minimum time to calculate the path. When this happens the selected id is positioned at the end of the list to cycle dynamically the priority, and finally, the timer starts again. This method lets the enemies' needs balance the computation times, allowing the thread to work almost constantly.

In addition, the threads need to get the positions of all the enemies, but Unity's API can only be used in the main thread. To solve this problem, I defined a class with the purpose of storing the data necessary to update the NavMesh obstacles. And when the computation needs to be done, the thread asks the main thread for the necessary information via events and allocates them in instances of that class.

These implementations allowed me to use mutex only when:

  • Adding or removing an enemy from a thread.
  • The thread evaluates which enemy's path needs to be recalculated.

Chess

Chess

This game is an online chess game, and can look simple, but has a peculiarity, depending in the screen the player is, the connection could be server-client or P2P.

This game was developed with the framework SFML, making use of their TCP sockets, and I was responsible for developing the network part.

Implementation

We wanted to give the users the capability to choose between being a server or a client.

To make this possible, when the application starts, it asks the user what they want to be. If they choose server mode, they will open a port to make possible the connection. And if they choose client mode, they must type the IP in order to connect with the server.

The server handles the next client requests:

  • Connect To Server
  • Login
  • Create Room
  • Join Room as Player
  • Join Room as Spectator
  • Send Message
  • Ready to Play

Once the match has begun, all the clients' sockets inside the room are closed, and connection P2P starts. In this state the "ruler" is the client who has been inside the room the longest.

During the match the ruler handles the next requests:

  • Exit Room
  • Send Message
  • Select Piece
  • Deselect Piece
  • Move Piece
  • Pawn Promotion
  • Castle
  • En Passsant
